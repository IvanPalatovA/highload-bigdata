# Журнал работ (Вариант 93)

## ЛР1. Стенд и сбор данных

### Принятые решения по сборщику
1. **Источник и фильтрация**: Источник GH Archive отдаёт почасовые сжатые файлы `.json.gz`. Сборщик скачивает поток через `requests.get(..., stream=True)`, распаковывает его на лету через `zlib.decompressobj` без загрузки всего архива в ОЗУ (укладываясь в лимит 512 МБ) и оставляет только события из `SOURCE_FILTER=CreateEvent,DeleteEvent,ReleaseEvent`.
2. **Ключ и время события**: В качестве `event_key` выбран уникальный идентификатор события GitHub `id`. Время `event_time` берётся из поля `created_at` и нормализуется к ISO 8601 UTC с миллисекундами (`.000Z`).
3. **Атомарность и сохранение позиции**: Каждый часовой файл сначала записывается во временный файл `.tmp-*.jsonl.gz`, после чего атомарно переименовывается через `os.replace`. Список обработанных часов и последних ключей сохраняется в `/data/raw/state/`, что исключает появление дублей при перезапуске службы.
4. **Ротация и метрики**: После закрытия каждого файла проверяется суммарный объём `stream` и `history`; при превышении `COLLECTOR_RAW_LIMIT_GB=20` удаляются самые старые файлы. На порту `9101/metrics` поднят HTTP-сервер в формате Prometheus.

### Замеры объёмов
- Доля фильтра: из ~2160 событий/мин полного потока фильтр `CreateEvent,DeleteEvent,ReleaseEvent` оставляет ~180 событий/мин (~8,3% потока).
- Суточный объём после фильтра: ~200 МБ до сжатия, ~34 МБ после сжатия gzip (коэффициент сжатия ~5,8x).
- Оценка на 8 недель потока + 7 дней истории: 63 * 0,034 = 2,14 ГБ, что с запасом укладывается в лимит 20 ГБ.

## ЛР2. Форматы данных

### 1. Схема события в Avro (fastavro)
- Схема события определена в файле `schemas/event.avsc` (record `Event`, namespace `stand`).
- Поля `event_key` (string) и `event_time` (long с логическим типом `timestamp-millis`) — обязательные. Логический тип задает точное время события в миллисекундах UTC с начала эпохи Unix.
- Необязательные поля источника (`org_id`, `org_login`, `ref_type`, `ref`, `master_branch`, `description`, `pusher_type`) объявлены union-типами с `null` и дефолтным значением `"default": null`.
- Программа проверки `schemas/check.py` на fastavro проверила валидацию, прямое кодирование в бинарный поток и обратное декодирование для сырых данных:
  - Проверено 689 событий за час из `data/raw/history/dt=2026-10-10/gharchive-2026-10-10-12.jsonl.gz`: 0 ошибок валидации.
  - Сырой JSON (текст, несжатый): 350 885 байт (342.7 КБ)
  - Двоичный Avro (несжатый): 149 781 байт (146.3 КБ)
  - Сжатый gzip JSON: 59 901 байт (58.5 КБ)
  - Двоичный Avro + deflate: 65 795 байт (64.3 КБ)
  - Бинарный формат Avro без сжатия компактнее текстового JSON на **57.3%** за счёт бинарной сериализации чисел, флагов и отсутствия дублирования названий полей в каждой записи.

### 2. Анализ сырых данных в DuckDB и отличия выведенных типов
При разборе сырых файлов функцией `read_json_auto`:
- Выведенные типы DuckDB:
  - `event_key`: `VARCHAR` (совпадает со схемой Avro `string`).
  - `event_time`: `TIMESTAMP` (микросекундная точность DuckDB, в Avro — `long` с `logicalType: timestamp-millis`).
  - `received_at`: `TIMESTAMP` (DuckDB автоматически распознал ISO 8601 строку, в Avro — `string`).
  - `actor_id`, `repo_id`, `org_id`: `BIGINT` (совпадает с Avro `long`).
  - `public`: `BOOLEAN` (совпадает с Avro `boolean`).
  - Текстовые поля: `VARCHAR` (совпадает с Avro `string`).
  - Hive-колонки `dt` (DATE) и `hour` (VARCHAR): движок автоматически извлек их из структуры каталогов `dt=.../hour=...`. Чтобы исключить конфликты при сохранении, ключ партиции слоя очищенных данных назван `event_date`.
- Повторы по ключу: запрос проверки `count(*) - count(distinct event_key)` на всем слое (122 811 записей) показал **0 дубликатов**.

### 3. Преобразование в Parquet и замеры производительности
Запрос `jobs/to_parquet.sql` выполняет дедупликацию по `event_key`, явное приведение типов и сохранение в `data/duckdb/parquet/events` с `PARTITION_BY (event_date)` и флагом `OVERWRITE_OR_IGNORE true` (повторный запуск перезаписывает файлы, не создавая дубликатов).

**Бенчмарк аналитического запроса (сутки 2026-10-10, группировка по часам и типам событий):**
```sql
SELECT strftime(event_time, '%Y-%m-%d %H:00') as hour_slot, type, count(*), count(distinct actor_login)
FROM ...
GROUP BY 1, 2 ORDER BY 1, 2;
```
- **Сырой JSON Lines (.jsonl.gz)**:
  - 3 запуска: 0.024 с, 0.023 с, 0.024 с
  - Медиана: **0.024 с**
  - Объём каталога на диске: **1.4 МБ** (несжатый текст ~8.4 МБ)
- **Колоночный формат Parquet (.parquet)**:
  - 3 запуска: 0.007 с, 0.006 с, 0.006 с
  - Медиана: **0.006 с**
  - Объём каталога на диске: **1.7 МБ**
- **Итог**: Запрос к Parquet выполняется в **4.0 раза быстрее** (0.006 с против 0.024 с) за счёт колоночного чтения только необходимых столбцов (`event_time`, `type`, `actor_login`) и отсутствия накладных расходов на потоковую распаковку gzip и парсинг текстового JSON.

### 4. Эволюция схемы (v1 -> v2) и совместимость
- В схему `schemas/event.avsc` добавлено новое опциональное поле `actor_avatar_url` со значением по умолчанию `null` (коммит Schema v2).
- Программой `schemas/check.py` проверена совместимость в обоих направлениях:
  1. **v1 -> v2 (обратная совместимость / backward compatibility)**: Данные, записанные по схеме v1, прочитаны схемой v2. Поле `actor_avatar_url` автоматически заполнено значением по умолчанию (`null`).
  2. **v2 -> v1 (прямая совместимость / forward compatibility)**: Данные, записанные по схеме v2, прочитаны схемой v1. Новое поле `actor_avatar_url` безопасно пропущено декодером Avro.
  3. **Совместимость схемы**: полная (**full compatibility**).
- Запросом `jobs/to_parquet_v2.sql` записаны новые сутки (`2026-10-16`) с полем `actor_avatar_url`. Старые партиции (`2026-10-08` .. `2026-10-14`) остались без этого столбца.
- При выполнении общего запроса с `union_by_name = true` DuckDB корректно объединяет партиции с разной структурой колонок: для старых суток `actor_avatar_url` возвращает `NULL` (120 760 строк), для новых суток значение заполнено (2 051 строк).

## ЛР3. Озеро данных

### Решения по слоям и очистке
- Garage используется как S3-совместимое хранилище bucket `lake`. Закрытые файлы сборщика копируются в `raw/` с тем же путём, что и на диске; перед загрузкой проверяется существование ключа, поэтому повторный запуск не создаёт дубликат.
- Clean-слой хранится в `clean/events/event_date=...` в Parquet zstd с `ROW_GROUP_SIZE=122880`: параметры выбраны измерениями ЛР2.
- `jobs/clean.sql` читает raw за D и D+1: файл, полученный на следующий день, может содержать опоздавшее событие суток D. Правила очистки: отбрасываются пустой `event_key`, записи с неверным временем и события вне фильтра варианта; дубликаты выбираются по `event_key`, остаётся наиболее поздняя запись по `received_at`; все поля приводятся к типам схемы Avro, `event_time` и раздел `event_date` — UTC.
- Для GH Archive ожидаемы повторы при повторной загрузке часа, неполные/ещё публикуемые часовые архивы и события вне фильтра в исходном архиве. Первые два компенсируются повтором сборщика и дедупликацией clean-слоя, последнее отбрасывается фильтром.

### Проверка и хранение
- Повторный запуск `clean.sql` перезаписывает только партицию `event_date=D` (`OVERWRITE_OR_IGNORE`), поэтому не добавляет копии. Число clean-событий может быть меньше raw за сутки: удаляются повторы/невалидные записи, а события D из файла, полученного D+1, добавляются к правильной партиции.
- Срок обоих слоёв — 63 суток: он покрывает восемь недель потока и семь суток истории в пределах диска стенда. `jobs/retention.py` удаляет только S3-объекты партиций старше срока; `--dry-run` не меняет данные.



## ЛР4. Таблицы Iceberg

### 1. Конфигурация и схема таблицы
- Таблица `lake.clean.events` зарегистрирована в REST-каталоге Lakekeeper (`http://catalog:8181/catalog`, warehouse `lake`, пространство имен `clean`). Данные хранятся в объектном хранилище S3 (SeaweedFS, bucket `lake`).
- Схема включает 18 столбцов исходной Avro-схемы (версия v1) с явным скрытым партиционированием по дням:
  `PARTITIONED BY (days(event_time))`
- В отличие от партиционирования Hive, в Iceberg колонка партиционирования не дублируется как виртуальная колонка каталогов, а вычисляется неявно движком из реального поля `event_time`.
- Подключение DuckDB настроено через `data/duckdb/init.sql` с загрузкой расширений `httpfs` и `iceberg`, секретами `s3sec` и `ic`, и монтированием `ATTACH 'lake' AS lake (TYPE iceberg, SECRET ic, ACCESS_DELEGATION_MODE 'none')`.
- Подключение Spark настроено через `conf/spark/spark-defaults.conf` с классом каталога `org.apache.iceberg.spark.SparkCatalog` и типом `rest`.

### 2. Загрузка данных и идемпотентность
- Загрузка исторического среза (2026-10-08 — 2026-10-14, 120 760 строк) и потоковых порций (2026-10-16, 2026-10-17, 2026-10-19, 2026-10-25, 2026-10-26) выполнена запросами `jobs/iceberg_load.sql`.
- Идемпотентность достигается тем, что перед записью порции выполняется удаление данных за целевой интервал:
  `DELETE FROM lake.clean.events WHERE event_time >= day AND event_time < day + INTERVAL '1 day';`
- Общий объём таблицы после начальной загрузки: **139 530 строк**.

### 3. Отсечение файлов по предикату (Predicate Pushdown / Partition Pruning)
Сравнение выполнения аналитического запроса в DuckDB с замером прочитанных файлов через `EXPLAIN ANALYZE`:
```sql
SELECT strftime(event_time, '%Y-%m-%d %H:00') as hour_slot, type, count(*), count(distinct actor_login)
FROM lake.clean.events
[WHERE event_time >= TIMESTAMPTZ '2026-10-10 00:00:00+00' AND event_time < TIMESTAMPTZ '2026-10-11 00:00:00+00']
GROUP BY 1, 2 ORDER BY 1, 2;
```
- **Без предиката (сканирование всей таблицы)**:
  - Прочитано файлов (`Total Files Read`): **12 файлов**
  - Строк обработано: **139 530 строк**
- **С предикатом по event_time за одни сутки (2026-10-10)**:
  - Прочитано файлов (`Total Files Read`): **1 файл**
  - Строк обработано: **16 904 строки**
- **Вывод**: благодаря манифестам Iceberg и скрытому партиционированию `days(event_time)` движок DuckDB выполняет отсечение файлов на уровне метаданных без обращения к S3 для остальных 11 партиций, сокращая ввод-вывод в **12 раз**.

### 4. Снимки, Time Travel и откат (Rollback)
- История таблицы представлена цепочкой неизменяемых снимков (snapshots). Снимок хранит ссылки на манифесты и файлы данных.
- **Time Travel**: запрос на чтение состояния таблицы на момент конкретного снимка через Spark:
  `SELECT count(*) FROM lake.clean.events VERSION AS OF 3125082485831910116;` возвращает **120 760 строк** (состояние сразу после загрузки истории, до потока).
- **Ошибочная запись и откат**:
  - Состояние до ошибки: **139 530 строк** (снимок `195395005001122634`).
  - Выполнена ошибочная вставка дублирующих данных: строк стало **143 231**.
  - Выполнен откат процедуры Spark:
    `CALL lake.system.rollback_to_snapshot('clean.events', 195395005001122634);`
  - Число строк мгновенно вернулось к исходным **139 530 строкам**. Откат меняет лишь указатель текущего снимка таблицы в каталоге, не требуя перезаписи данных.

### 5. Уплотнение файлов (Compaction) и истечение снимков (Expire Snapshots)
- Для имитации потоковой записи мелкими порциями в сутках `2026-10-26` данные были записаны отдельными часовыми батчами.
- **До уплотнения**:
  - Всего файлов в таблице: **16**
  - В партиции `event_time_day=2026-10-26`: **5 файлов**
  - Всего снимков: **13**
- Выполнена процедура уплотнения через Spark:
  `CALL lake.system.rewrite_data_files(table => 'clean.events');`
- **После уплотнения**:
  - Всего файлов в таблице: **12**
  - В партиции `event_time_day=2026-10-26`: **1 файл** (5 мелких файлов объединены в 1 файл размером 436 728 байт)
  - Партиции, в которых было менее 5 файлов, процедура не затронула (пороговое значение по умолчанию Iceberg).
- **Истечение снимков**:
  - Вызов: `CALL lake.system.expire_snapshots(table => 'clean.events', older_than => TIMESTAMP '2099-01-01 00:00:00', retain_last => 1);`
  - Количество снимков сократилось с **14 до 1**.
  - Удалено 7 ставших ненужными файлов данных и 8 файлов манифестов, освободив место в S3.
