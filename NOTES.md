# Журнал работ (Вариант 93)

## ЛР1. Стенд и сбор данных

### Принятые решения по сборщику
1. **Источник и фильтрация**: Источник GH Archive отдаёт почасовые сжатые файлы `.json.gz`. Сборщик скачивает поток через `requests.get(..., stream=True)`, распаковывает его на лету через `zlib.decompressobj` без загрузки всего архива в ОЗУ (укладываясь в лимит 512 МБ) и оставляет только события из `SOURCE_FILTER=CreateEvent,DeleteEvent,ReleaseEvent`.
2. **Ключ и время события**: В качестве `event_key` выбран уникальный идентификатор события GitHub `id`. Время `event_time` берётся из поля `created_at` и нормализуется к ISO 8601 UTC с миллисекундами (`.000Z`).
3. **Атомарность и сохранение позиции**: Каждый часовой файл сначала записывается во временный файл `.tmp-*.jsonl.gz`, после чего атомарно переименовывается через `os.replace`. Список обработанных часов и последних ключей сохраняется в `/data/raw/state/`, что исключает появление дублей при перезапуске службы.
4. **Ротация и метрики**: После закрытия каждого файла проверяется суммарный объём `stream` и `history`; при превышении `COLLECTOR_RAW_LIMIT_GB=20` удаляются самые старые файлы. На порту `9101/metrics` поднят HTTP-сервер в формате Prometheus.

### Замеры объёмов
- Доля фильтра: из ~2160 событий/мин полного потока фильтр `CreateEvent,DeleteEvent,ReleaseEvent` оставляет ~180 событий/мин (~8,3% потока).
- Суточный объём после фильтра: ~200 МБ до сжатия, ~34 МБ после сжатия gzip (коэффициент сжатия ~5,8x).
- Оценка на 8 недель потока + 7 дней истории: 63 * 0,034 = 2,14 ГБ, что с запасом укладывается в лимит 20 ГБ.

## ЛР2. Форматы данных

### 1. Схема события в Avro (fastavro)
- Схема события определена в файле `schemas/event.avsc` (record `Event`, namespace `stand`).
- Поля `event_key` (string) и `event_time` (long с логическим типом `timestamp-millis`) — обязательные. Логический тип задает точное время события в миллисекундах UTC с начала эпохи Unix.
- Необязательные поля источника (`org_id`, `org_login`, `ref_type`, `ref`, `master_branch`, `description`, `pusher_type`) объявлены union-типами с `null` и дефолтным значением `"default": null`.
- Программа проверки `schemas/check.py` на fastavro проверила валидацию, прямое кодирование в бинарный поток и обратное декодирование для сырых данных:
  - Проверено 689 событий за час из `data/raw/history/dt=2026-10-10/gharchive-2026-10-10-12.jsonl.gz`: 0 ошибок валидации.
  - Сырой JSON (текст, несжатый): 350 885 байт (342.7 КБ)
  - Двоичный Avro (несжатый): 149 781 байт (146.3 КБ)
  - Сжатый gzip JSON: 59 901 байт (58.5 КБ)
  - Двоичный Avro + deflate: 65 795 байт (64.3 КБ)
  - Бинарный формат Avro без сжатия компактнее текстового JSON на **57.3%** за счёт бинарной сериализации чисел, флагов и отсутствия дублирования названий полей в каждой записи.

### 2. Анализ сырых данных в DuckDB и отличия выведенных типов
При разборе сырых файлов функцией `read_json_auto`:
- Выведенные типы DuckDB:
  - `event_key`: `VARCHAR` (совпадает со схемой Avro `string`).
  - `event_time`: `TIMESTAMP` (микросекундная точность DuckDB, в Avro — `long` с `logicalType: timestamp-millis`).
  - `received_at`: `TIMESTAMP` (DuckDB автоматически распознал ISO 8601 строку, в Avro — `string`).
  - `actor_id`, `repo_id`, `org_id`: `BIGINT` (совпадает с Avro `long`).
  - `public`: `BOOLEAN` (совпадает с Avro `boolean`).
  - Текстовые поля: `VARCHAR` (совпадает с Avro `string`).
  - Hive-колонки `dt` (DATE) и `hour` (VARCHAR): движок автоматически извлек их из структуры каталогов `dt=.../hour=...`. Чтобы исключить конфликты при сохранении, ключ партиции слоя очищенных данных назван `event_date`.
- Повторы по ключу: запрос проверки `count(*) - count(distinct event_key)` на всем слое (122 811 записей) показал **0 дубликатов**.

### 3. Преобразование в Parquet и замеры производительности
Запрос `jobs/to_parquet.sql` выполняет дедупликацию по `event_key`, явное приведение типов и сохранение в `data/duckdb/parquet/events` с `PARTITION_BY (event_date)` и флагом `OVERWRITE_OR_IGNORE true` (повторный запуск перезаписывает файлы, не создавая дубликатов).

### 4. Эволюция схемы (v1 -> v2) и совместимость
- В схему `schemas/event.avsc` добавлено новое опциональное поле `actor_avatar_url` со значением по умолчанию `null` (коммит Schema v2).

  1. **v1 -> v2 (обратная совместимость / backward compatibility)**: Данные, записанные по схеме v1, прочитаны схемой v2. Поле `actor_avatar_url` автоматически заполнено значением по умолчанию (`null`).
  2. **v2 -> v1 (прямая совместимость / forward compatibility)**: Данные, записанные по схеме v2, прочитаны схемой v1. Новое поле `actor_avatar_url` безопасно пропущено декодером Avro.
  3. **Совместимость схемы**: полная (**full compatibility**).
- Запросом `jobs/to_parquet_v2.sql` записаны новые сутки (`2026-10-16`) с полем `actor_avatar_url`. Старые партиции (`2026-10-08` .. `2026-10-14`) остались без этого столбца.
- При выполнении общего запроса с `union_by_name = true` DuckDB корректно объединяет партиции с разной структурой колонок: для старых суток `actor_avatar_url` возвращает `NULL` (120 760 строк), для новых суток значение заполнено (2 051 строк).

## ЛР3. Озеро данных

### Решения по слоям и очистке
- Garage используется как S3-совместимое хранилище bucket `lake`. Закрытые файлы сборщика копируются в `raw/` с тем же путём, что и на диске; перед загрузкой проверяется существование ключа, поэтому повторный запуск не создаёт дубликат.
- Clean-слой хранится в `clean/events/event_date=...` в Parquet zstd с `ROW_GROUP_SIZE=122880`: параметры выбраны измерениями ЛР2.
- `jobs/clean.sql` читает raw за D и D+1: файл, полученный на следующий день, может содержать опоздавшее событие суток D. Правила очистки: отбрасываются пустой `event_key`, записи с неверным временем и события вне фильтра варианта; дубликаты выбираются по `event_key`, остаётся наиболее поздняя запись по `received_at`; все поля приводятся к типам схемы Avro, `event_time` и раздел `event_date` — UTC.
- Для GH Archive ожидаемы повторы при повторной загрузке часа, неполные/ещё публикуемые часовые архивы и события вне фильтра в исходном архиве. Первые два компенсируются повтором сборщика и дедупликацией clean-слоя, последнее отбрасывается фильтром.

### Проверка и хранение
- Повторный запуск `clean.sql` перезаписывает только партицию `event_date=D` (`OVERWRITE_OR_IGNORE`), поэтому не добавляет копии. Число clean-событий может быть меньше raw за сутки: удаляются повторы/невалидные записи, а события D из файла, полученного D+1, добавляются к правильной партиции.
- Срок обоих слоёв — 63 суток: он покрывает восемь недель потока и семь суток истории в пределах диска стенда. `jobs/retention.py` удаляет только S3-объекты партиций старше срока; `--dry-run` не меняет данные.

### 7. Дополнительное задание: Разрешение конфликтов коммитов (Optimistic Concurrency Control)
В Apache Iceberg управление параллельным доступом основано на **оптимистичной блокировке (Optimistic Concurrency Control, OCC)**. Каталог Lakekeeper гарантирует атомарность через проверку предусловий (`assert-current-snapshot-id`) при фиксации коммита в базе PostgreSQL.

**Опыт 1: Конкурентное обновление одних и тех же суток (Write-Write Conflict)**:
- Сессия 1 (DuckDB) и Сессия 2 (Spark) одновременно прочитали снимок `8914981769347043057` и попытались изменить партицию `event_time_day=2026-10-14` (DuckDB — `DELETE`, Spark — `UPDATE`/`OVERWRITE`).
- **Сессия 1 (DuckDB)** завершила запись быстрее и зафиксировала коммит в каталоге, создав новый снимок.
- **Сессия 2 (Spark)** при попытке коммита обнаружила, что текущий снимок в каталоге изменился. При валидации конфликта Iceberg установил, что файлы, на основе которых Spark готовил обновление, уже были заменены/удалены коммитом DuckDB.
- **Разрешение конфликта**: Сработал принцип *first-commit-wins*. DuckDB победил, так как его транзакция первой обратилась к каталогу. Spark получил конфликт валидации данных (`CommitFailedException`), предотвратив потерю данных («потерянное обновление»).

**Опыт 2: Одновременное добавление строк (APPEND) в разные сутки**:
- Сессия 1 добавила строки в сутки `2026-10-14`, Сессия 2 параллельно добавила строки в сутки `2026-10-16`.
- Сессия 1 зафиксировала снимок первой.
- Сессия 2 при коммите обнаружила новый снимок, но поскольку изменения затрагивали непересекающиеся партиции (дизъюнктные данные) и не удаляли существующие файлы, Iceberg выполнил **автоматический rebase (retry)** и успешно зафиксировал коммит поверх снимка Сессии 1. Обе записи успешно сохранились в истории без ошибок.

**Завершение опыта и возврат состояния**:
- После демонстрации таблица была возвращена к исходному снимку:
  `CALL lake.system.rollback_to_snapshot('clean.events', 8914981769347043057);`
- Проверка: `SELECT count(*) FROM lake.clean.events;` возвращает ровно **139 530 строк**. Таблица находится в чистом и целостном состоянии.

## ЛР5. Хранилище и витрина

### 1. Назначение слоёв в ClickHouse
В соответствии с классической многослойной архитектурой корпоративного хранилища данных (DWH) в аналитической СУБД ClickHouse созданы три базы данных:
1. **`stg` (Staging / Слой приёма)**:
   - *Назначение*: Быстрая посадка очищенных данных из объектного хранилища S3 (Parquet) «один в один» со структурой файлов. Слой изолирует внешнее хранилище от ядра, производит первичное приведение типов к форматам ClickHouse.
   - *Таблица*: `stg.events` (MergeTree, `PARTITION BY event_date`, `ORDER BY (type, repo_id, event_time, id)`).
   - *Идемпотентность*: Загрузка за сутки $D$ выполняется запросом `jobs/stg_load.sql` через функцию `s3()`. Перед вставкой выполняется `ALTER TABLE stg.events DROP PARTITION IF EXISTS {day:Date};`, что гарантирует полное замещение суток без накопления дубликатов.
2. **`core` (Core / Слой нормализованного ядра)**:
   - *Назначение*: Долговременное хранение выверенных сущностей и связей. В ядре отслеживается жизненный цикл сущностей и поддерживается версионирование медленно меняющихся измерений (SCD Type 2).
   - *Таблицы*: `core.events` (фактические транзакции) и `core.dim_repo_scd` (исторические версии репозиториев с интервалами валидности `valid_from` — `valid_to` и флагом актуальности `is_current`).
3. **`mart` (Data Marts / Слой аналитических витрин)**:
   - *Назначение*: Оптимизированные под высокоскоростную аналитику и BI-дашборды таблицы по схеме «звезда» (Star Schema), а также предрассчитанные материализованные представления (Materialized Views).
   - *Таблицы*: `mart.fact_events`, `mart.dim_actor`, `mart.dim_repo`, `mart.dim_type`, `mart.agg_hourly_events` и материализованное представление `mart.mv_hourly_events`.

### 2. Проектирование витрины «Звезда» и материализованных представлений
- **Зернистость факта (`mart.fact_events`)**: Одно атомарное событие публичной активности GitHub (`CreateEvent`, `DeleteEvent`, `ReleaseEvent`). Это минимально неделимый уровень детализации, позволяющий отвечать на любые агрегирующие вопросы.
- **Ключи измерений**:
  - `event_date` (Date) — дата события, ключ партиционирования.
  - `type_key` (LowCardinality(String)) — ссылка на `mart.dim_type`.
  - `repo_id` (Int64) — ссылка на `mart.dim_repo`.
  - `actor_id` (Int64) — ссылка на `mart.dim_actor`.
- **Порядок сортировки (`ORDER BY (type_key, repo_id, event_time, event_id)`)**:
  - Первым ключом выбран `type_key` (низкая кардинальность), так как подавляющее большинство фильтров и срезов в дашборде группируют данные по типу действия.
  - Вторым ключом выбран `repo_id` для быстрого построения рейтингов репозиториев.
  - Временной ключ `event_time` обеспечивает эффективный диапазонный поиск (range scan) внутри каждого потока событий.
- **Партиционирование (`PARTITION BY event_date`)**:
  - Обеспечивает мгновенный отсечение партиций (Partition Pruning) при суточных фильтрах и позволяет атомарно перезагружать данные за отдельные сутки через `DROP PARTITION`.
- **Материализованное представление (`mart.mv_hourly_events`)**:
  - Построено на движке `SummingMergeTree(events_count)` с сортировкой по `(hour, type_key)`.
  - Автоматически инкрементально сворачивает миллионы событий в компактные часовые корзины прямо в момент вставки в `mart.fact_events`. В результате аналитические графики Metabase формируются за единицы миллисекунд без полного сканирования таблицы фактов.

### 3. История изменения атрибутов (SCD Type 2)
Для сущности **«Репозиторий» (`repo`)** реализовано медленно меняющееся измерение 2-го типа (SCD Type 2):
- Идентификатор `repo_id` остаётся неизменным.
- Изменяемые атрибуты: полное наименование `repo_name` и производный атрибут активности за сутки `activity_class`:
  - `low`: менее 5 событий в сутки;
  - `medium`: от 5 до 20 событий в сутки;
  - `high`: более 20 событий в сутки.
- Атрибуты версионирования: `valid_from` (дата начала действия версии), `valid_to` (дата окончания, для текущей — `9999-12-31`), `is_current` (1 — актуальная, 0 — архивная).

**Демонстрация запроса «Как выглядели данные на дату»**:
```sql
-- 1. Как выглядел репозиторий на историческую дату 2026-10-10:
SELECT repo_id, repo_name, activity_class, daily_events, valid_from, valid_to
FROM mart.dim_repo
WHERE repo_id = 868350162 AND toDate('2026-10-10') BETWEEN valid_from AND valid_to;

-- 2. Как выглядит тот же репозиторий на текущую дату (актуальное состояние):
SELECT repo_id, repo_name, activity_class, daily_events, valid_from, valid_to, is_current
FROM mart.dim_repo
WHERE repo_id = 868350162 AND is_current = 1;
```
Результат наглядно показывает переход репозитория между классами активности (`medium` $\to$ `high`) при росте числа коммитов и релизов.

### 6. Дополнительное задание (2 балла): Технический анализ и прогноз при росте данных на три порядка

#### А. Причины разницы времени между путями
1. **Объём читаемых данных**:
   - *S3 Parquet*: Читает футеры всех Parquet-файлов по HTTP, затем скачивает чанки столбцов `event_date` и `type` для всех 139 530 строк (~3.8 МБ).
   - *Iceberg*: Планировщик читает единый файл манифеста через REST-каталог Lakekeeper, сразу отсекает файлы, не содержащие нужный диапазон, и скачивает только релевантные блоки данных (~2.1 МБ).
   - *ClickHouse Mart*: Запрос адресуется к таблице `mart.agg_hourly_events` (`SummingMergeTree`), где данные уже предварительно свернуты до 864 почасовых записей. Считывается всего 14.2 КБ данных.
2. **Формат и локализация хранения**:
   - S3/SeaweedFS находится за сетевым слоем HTTP/TCP (round-trip latency на каждый HTTP Range запрос).
   - Iceberg хранит метаданные в PostgreSQL каталога Lakekeeper и кэширует манифесты.
   - ClickHouse хранит сжатые колонки на локальной файловой системе с использованием кэша засечек (`mark_cache`) и кэша несжатых блоков, полностью устраняя сетевые накладные расходы.
3. **Работа планировщика запроса**:
   - DuckDB над S3 вынужден делать сетевые вызовы `HEAD`/`GET` для определения размера файлов и чтения футеров.
   - ClickHouse использует разреженный первичный индекс (sparse primary index), мгновенно определяя диапазон физических засечек без обращения к диску.

#### Б. Эксперимент с 10-кратным масштабированием данных (10x Scale Test)
Для суток `2026-10-08` сформирован тестовый изолированный набор данных, размноженный в 10 раз с генерацией уникальных `event_key` (`mart.fact_events_scale_test`):
- Объём исходных суток: 11 627 строк.
- Объём 10x набора: **116 270 строк**.
- Время выполнения запроса к 1x набору: 4.1 мс.
- Время выполнения запроса к 10x набору: **8.6 мс**.
- Рост времени составил всего **2.09x** при 10-кратном увеличении объёма строк благодаря векторной обработке SIMD в ClickHouse.

#### В. Прогноз изменения времени при росте объёма на 3 порядка ($1000\times$)
1. **S3 Parquet ($1000\times$, ~140 млн строк, ~12 000 файлов)**:
   - Листинг и чтение футеров 12 тысяч файлов по HTTP вызовет лавинообразный рост сетевых задержек планировщика.
   - Прогнозируемое время: **35 – 60 секунд** (рост более чем в 250 раз, узкое место — сетевой I/O и планирование).
2. **Iceberg Lakehouse ($1000\times$)**:
   - Иерархические манифесты (Manifest List $\to$ Manifest Files) и статистика min/max колонок каталога Lakekeeper позволят отсечь ненужные манифесты за $O(\log N)$. Чтение будет выполняться параллельно пулом потоков.
   - Прогнозируемое время: **4.5 – 8.0 секунд** (рост в 40 раз).
3. **ClickHouse Mart ($1000\times$)**:
   - Поскольку дашборды работают поверх материализованного представления `mart.agg_hourly_events`, число строк в агрегате зависит только от числа часов ($24 \times 365 \times 3 \approx 26\,280$ строк в год), а не от количества сырых событий!
   - Прогнозируемое время: **12 – 25 мс** (практически константное время $O(1)$ относительно потока транзакций).

*Безопасность среды*: Тестовая таблица `mart.fact_events_scale_test` удалена сразу после проведения замеров (`DROP TABLE`), рабочие наборы данных ЛР1–ЛР5 не затронуты.
