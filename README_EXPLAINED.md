# 📘 Лабораторная работа 4: Руководство «для чайников»
## Что вообще произошло, зачем всё это нужно и как отвечать на вопросы преподавателя

---

## 1. В чём главная идея лабы? (Объяснение на пальцах)

В **ЛР3** мы просто скопировали Parquet-файлы в S3 по папкам вида `clean/events/event_date=2026-10-10/part-0.parquet`.
Это классический подход **Hive**:
- База данных считает, что структура каталогов на диске — это и есть структура таблицы.
- Чтобы узнать, какие файлы есть в таблице, движок должен сделать *листинг* (запросить у S3 список всех файлов). Если файлов миллион — это занимает минуты!
- Если запись прервалась на середине — в папке останутся половинчатые файлы (нет транзакционности).
- Нельзя легко сделать откат ошибки или посмотреть, как таблица выглядела вчера.

В **ЛР4** мы перевели таблицу в современный формат **Apache Iceberg**:
- Теперь таблица — это не просто папка с файлами.
- Таблица управляется через **каталог метаданных** (в нашем стенде — сервис `Lakekeeper`).
- Каждый раз, когда мы что-то пишем или удаляем, создаётся **снимок (Snapshot)**. Снимок — это список файлов, которые актуальны именно сейчас.
- Движкам (DuckDB, Spark) больше не нужно опрашивать S3 «покажи, какие файлы лежат в папке». Движок спрашивает у каталога: *«Какой сейчас текущий снимок?»*, читает маленький файл метаданных и **сразу знает точные имена всех нужных файлов**!

---

## 2. Кто есть кто на нашем стенде?

1. **S3 (SeaweedFS)** — хранилище данных (наш личный Amazon S3). Там лежат сами файлы данных (`.parquet`) и файлы метаданных Iceberg (`metadata.json`, `.avro`).
2. **Lakekeeper (REST Catalog)** — диспетчер метаданных. Он хранит информацию о том, какие таблицы существуют, какая у них текущая схема и какой снимок является актуальным в данный момент. Сам он хранит эту информацию в базе данных `Postgres` (`catalog-db`).
3. **DuckDB** — быстрый легковесный аналитический SQL-движок. В лабе мы используем его для аналитических запросов и для загрузки суточных порций.
4. **Apache Spark** — тяжелая артиллерия для пакетной обработки и обслуживания (maintenance). Через него мы делали создание таблицы (DDL), уплотнение файлов (compaction), откат снимков (rollback) и удаление старых снимков (expire snapshots).

## 3. Что мы сделали шаг за шагом

### Шаг 1. Создали таблицу Iceberg `lake.clean.events`
Мы создали таблицу со схемой из 18 колонок (те же самые поля, что были в нашей Avro-схеме из ЛР2) и указали:
```sql
PARTITIONED BY (days(event_time));
```
**Фишка (Скрытое партиционирование / Hidden Partitioning):**
В старом Hive нам приходилось создавать отдельную искусственную колонку `event_date` и при запросах писать `WHERE event_date = '2026-10-10'`. Если пользователь случайно написал `WHERE event_time >= '...'`, Hive сканировал всю таблицу!
В Iceberg партиционирование скрытое: колонка в таблице одна — `event_time` (timestamp). А Iceberg сам знает, что дни вычисляются из этого поля. Запрос `WHERE event_time >= '2026-10-10'` автоматически отсекает все остальные дни!

### Шаг 2. Загрузили данные (139 530 строк)
Мы взяли очищенные данные за 7 дней истории (2026-10-08 — 2026-10-14) и несколько дней потока.
Загружали по дням.
**Как обеспечили идемпотентность?**
Перед вставкой дня мы делали:
```sql
DELETE FROM lake.clean.events WHERE event_time >= day AND event_time < day + INTERVAL '1 day';
```
Если скрипт упадет или запустится повторно, он сначала сотрет этот день и запишет заново — никаких дубликатов!

### Шаг 3. Доказали отсечение файлов (Predicate Pushdown)
Мы выполнили команду `EXPLAIN ANALYZE`:
- **Без WHERE**: DuckDB прочитал **12 файлов** (все 139 530 строк).
- **С WHERE по одной дате**: DuckDB прочитал ровно **1 файл** (16 904 строки).
Остальные 11 файлов даже не запрашивались у S3. Это экономит трафик, память и время.

### Шаг 4. Снимки и Time Travel (Путешествие во времени)
Каждая операция записи в Iceberg создаёт `snapshot`.
Мы выполнили запрос:
```sql
SELECT count(*) FROM lake.clean.events VERSION AS OF 3125082485831910116;
```
И получили `120760` строк — ровно столько, сколько было в таблице до того, как мы залили потоковые данные!
То есть мы можем заглянуть в прошлое без восстановления бекапов.

### Шаг 5. Ошибочная запись и мгновенный откат (Rollback)
Мы сымитировали аварию: случайно сделали дублирующую вставку. Строк стало 143 231.
Потом вызвали процедуру:
```sql
CALL lake.system.rollback_to_snapshot('clean.events', 195395005001122634);
```
И таблица моментально вернулась в состояние 139 530 строк!
**Почему это происходит мгновенно?**
Потому что Iceberg не удаляет строки и не откатывает транзакции в файлах. Он просто говорит каталогу: *«Считай теперь активным предыдущий снимок»*. Это операция изменения одной строчки в метаданных!

### Шаг 6. Компакция (Уплотнение мелких файлов)
Когда данные приходят небольшими порциями (например, каждый час по чуть-чуть), в озере появляется так называемая «болезнь мелких файлов» (small files problem): миллион файлов по 10 КБ перегружают сеть и файловую систему.
Мы сымитировали эту ситуацию: разбили сутки `2026-10-26` на 5 мелких часовых файлов.
Затем вызвали процедуру:
```sql
CALL lake.system.rewrite_data_files(table => 'clean.events');
```
Spark взял эти 5 мелких файлов, склеил их в один красивый оптимизированный Parquet-файл (436 КБ) и создал новый снимок.
При этом читатели в этот момент продолжали спокойно читать старые файлы без блокировок (ACID-изоляция).

### Шаг 7. Очистка старых снимков (Expire Snapshots)
После уплотнения старые 5 файлов остались лежать на диске (вдруг кто-то захочет сделать Time Travel).
Чтобы освободить место, мы вызвали:
```sql
CALL lake.system.expire_snapshots(table => 'clean.events', older_than => TIMESTAMP '2099-01-01', retain_last => 1);
```
Iceberg удалил старые снимки и физически стёр из S3 файлы, на которые больше никто не ссылается (освободил память).

### Шаг 8. Эволюция схемы (Schema Evolution) без перезаписи файлов
Преподаватель спросит: *«Вы добавили новую колонку `actor_avatar_url`. Таблица перезаписывалась?»*
Ответ: **НЕТ!**
В классических базах данных добавление колонки часто требует переписать гигабайты файлов.
В Iceberg:
1. Каждой колонке присваивается числовой ID (`field-id`).
2. При вызове `ALTER TABLE ... ADD COLUMN actor_avatar_url STRING`:
   - Iceberg просто добавил запись о новом поле в JSON-файл метаданных.
   - Сами 12 файлов Parquet в S3 **вообще не трогались** (их хеши и пути абсолютно те же).
   - Когда мы читаем старые данные, движок видит, что в файле нет колонки с этим ID, и на лету подставляет `NULL`.

## 4. Возможные коварные вопросы преподавателя и как на них отвечать

| Вопрос преподавателя | Правильный ответ |
|----------------------|------------------|
| *Где хранятся метаданные Iceberg?* | Метаданные (снимки, манифесты) хранятся в S3 в папке `metadata/` в формате JSON и Avro. А ссылка на самый последний файл метаданных хранится в каталоге Lakekeeper (в базе Postgres). |
| *Чем скрытое партиционирование Iceberg лучше партиционирования Hive?* | В Hive партиция — это явная папка на диске (`dt=...`), и запрос должен фильтровать именно по этой колонке. В Iceberg партиционирование — это функция от существующего поля (`days(event_time)`). Пользователь может даже не знать, как партиционирована таблица, и просто писать привычный `WHERE event_time >= ...` — отсечение файлов сработает само. |
| *Почему Rollback выполняется мгновенно?* | Потому что это метаданная операция. Данные не перемещаются и не перезаписываются; в каталоге просто меняется указатель `current-snapshot-id` на идентификатор старого снимка. |
| *Что делает `rewrite_data_files`? Блокирует ли он чтение?* | Он читает мелкие файлы и перезаписывает их в меньшее количество крупных. Чтение не блокируется: старые файлы остаются доступными читателям до тех пор, пока новая порция не зафиксируется атомарным коммитом снимка. |
| *Зачем нужен `expire_snapshots`?* | После частых обновлений и компакции старые файлы данных продолжают занимать место в S3 для поддержки Time Travel. `expire_snapshots` удаляет метаданные старых снимков и физически стирает из хранилища осиротевшие (orphaned) файлы данных. |
| *Почему при добавлении колонки не нужно переписывать файлы?* | Iceberg использует адресацию колонок по ID (`field-id`), а не по именам или номерам позиций. При добавлении колонки обновляется только схема в метаданных; движки при чтении старых файлов, где этого ID нет, автоматически возвращают `NULL`. |
